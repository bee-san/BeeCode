# bee-fsrs in BeeCode

**The engine now lives in its own repository:
[`bee-san/bee-fsrs`](https://github.com/bee-san/bee-fsrs).**

This directory is a *vendored checkout* of the released `v0.2.0` sources, kept so that
BeeCode builds offline and on a fresh clone with no extra setup. It is not the place to
change the engine.

## Where to make changes

| Change | Where |
|---|---|
| FSRS mathematics, parameters, engine API | [`bee-san/bee-fsrs`](https://github.com/bee-san/bee-fsrs), then re-vendor |
| Which ratings BeeCode permits, due-queue order, persistence | `fsrs-adapter/` in this repository |

Editing the sources here without upstreaming them would silently fork the engine, and
the whole point of the split is that BeeCode and kanji_anki resolve the *same* tested
artifact. `FsrsProvenanceTest` asserts the vendored copy matches the released version
it claims to be.

| Package | `dev.bee:bee-fsrs` |

The commit is pinned because `0.2.0` is not a tag upstream — the only tag is `v0.1.0`, and
`version = "0.2.0"` in its `build.gradle.kts` moves with `main`. "The vendored copy is
v0.2.0" was therefore not a checkable statement on its own; the hash makes it one, the same
correction already applied to the FSRS-7 reference below.

Verified by diffing this directory against that commit: `src/` and `testdata/` are
byte-identical. Re-verify after any re-vendor with

```bash
git clone https://github.com/bee-san/bee-fsrs /tmp/bee-fsrs-upstream
diff -rq bee-fsrs/src /tmp/bee-fsrs-upstream/src && diff -rq bee-fsrs/testdata /tmp/bee-fsrs-upstream/testdata
```

One drift was found and fixed doing exactly that: the vendored `src/test/.../Json.kt` was a
commit behind upstream's `98f3ed7`, holding a raw `0x0C` form-feed byte where upstream had
replaced it with `''`. Test-parser only — no production mathematics differed — but it
is the kind of gap that grows silently, which is the argument for pinning the hash.

**BeeCode schedules with FSRS-7.** `fsrs-adapter` reaches for `Fsrs7Engine`, and
`FsrsProvenanceTest` pins that. FSRS-6 is vendored alongside it, not as a fallback but
because a schedule stored under 21 parameters is not reinterpretable under 35 — see
below.

## What FSRS-7 changed in BeeCode

Not a parameter bump. Three differences crossed the engine boundary and rippled outward:

| | FSRS-6.x | FSRS-7 |
|---|---|---|
| Parameters | 21 | 35 |
| Intervals | integer days | **fractional days** |
| Elapsed time | whole days, floored | **fractional days** |
| Forgetting curve | single power law | two power laws, blended by stability |
| Same-day reviews | separate branch below one day | continuous blend |

Each of those forced a change outside `bee-fsrs/`:

- **`persistence` schema version 2.** `interval_days`, `fsrs_elapsed_days`,
  `fsrs_max_interval_days`, and `fsrs_next_interval` were INTEGER. SQLite would have
  coerced a ten-minute interval toward zero, so the exact case FSRS-7 exists to schedule
  would have been the case that silently broke. `SchemaMigrationTest` builds a real
  version 1 database with review rows and proves they survive the upgrade.
- **`ProfileTransfer` format version 2.** The same widening in the export payload.
  Reading an older export still works, because JSON does not distinguish `3` from `3.0`;
  the bump is so a *version 1 build* refuses this payload with "upgrade BeeCode" rather
  than failing to parse `0.00694` as an integer.
- **`BeeCodeScheduler` stopped flooring elapsed time.** It used to floor to whole days,
  which was right for FSRS-6. Keeping it would have handed FSRS-7 an FSRS-6-shaped
  question and discarded the sub-day resolution at the boundary instead of in the engine.
- **`formatIntervalDays` in the domain.** "Next review in 0.00694 days" is the literal
  schedule and communicates nothing, so both clients share one formatter that picks a
  legible unit.

## Why FSRS-6 is still vendored

Stability and difficulty computed under 21 parameters do not mean the same thing under
35. Old rows stay **interpretable** — every transition records the algorithm label and
parameter hash, so a historical schedule can be replayed under the engine that produced
it — but they are not **reinterpretable** under the new one. Deleting the older engine
would turn every pre-migration row into a set of numbers with no stated meaning, which
is exactly what the per-transition audit exists to prevent.

## Why vendored rather than resolved from a repository

`dev.bee:bee-fsrs` is published to GitHub Packages, which requires a token with
`read:packages` even for a public package, and it is not on Maven Central yet. The
realistic options were:

- **A composite build or git submodule.** Both make a fresh clone or an offline build
  fail in ways that are annoying to diagnose, and Chaquopy's Android build is already
  the fragile part of this project.
- **JitPack.** Resolves from a tag without publishing, but adds a network dependency to
  every build including CI, and its build failures are opaque.
- **Vendoring the released sources.** Builds offline, needs no credentials, and the
  version claim is verified by a test.

Vendoring won on the trade, and the decision is reversible: `fsrs-adapter` is the only
module that imports `dev.bee.fsrs`, so switching to a resolved coordinate later changes
one dependency declaration.

## On the "FSRS 7" label

kanji_anki's README described its scheduler as "FSRS 7" while the code was FSRS-6.x, and
earlier revisions of this file spent several sections establishing that the label was
wrong. For BeeCode it no longer is: the engine really is FSRS-7 now, ported from
upstream's model rather than relabelled.

One line of that history is worth keeping, because the reasoning went wrong on the way
here. An early version of this file claimed upstream "has published no v7", which was
false — FSRS-7 was defined in `srs-benchmark` the whole time. The conclusion it was used
to support happened to be true for an entirely different reason: the parameter count. A
claim about what exists upstream was never the right evidence; the numbers in the code
were, and those are what `FsrsProvenanceTest` checks — now in the other direction.
